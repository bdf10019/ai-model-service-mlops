# 容器設定與未執行項目

日期：2026-09-14；0.3.0重新盤點。**Docker／Compose 目前未可用；未安裝、拉取映像、建置或執行容器。** 最新實際狀態保存於 `reports/container-readiness-0.3.0.json`；WSL/Docker系統安裝、重啟及大型下載不在本輪授權。

已建立多階段 `infra/Dockerfile`，以鎖版 pnpm 建置前端、鎖版 Python runtime 執行同一個控制台；使用非 root、只讀根檔案系統、drop capabilities、loopback host port、健康檢查及作品內持久狀態。設計依 [Docker 多階段建置文件](https://docs.docker.com/build/building/multi-stage/)及 [Compose 健康檢查文件](https://docs.docker.com/compose/how-tos/startup-order/)核對，尚未實跑。

`infra/compose.fixture.yaml` 只涵蓋**明示 Fixture 控制台容器**。不夾帶私人 DB、權重、Windows DLL 或既有測試報告；使用獨立 `state/container-console`。端口 `127.0.0.1:8128` 避開現有本機 8120。容器內 0.0.0.0 不等於 host 對外公開。

基底映像沒有杜撰 digest。取得系統與必要下載授權後，核對官方 Node 24 bookworm slim、Python 3.11 slim 的固定 digest／授權／大小，設定 `NODE_IMAGE=docker.io/library/node@sha256:<已核對值>` 與 `PYTHON_IMAGE=docker.io/library/python@sha256:<已核對值>`，再執行 `scripts/container-verify.ps1 -Build`。脚本不安裝系統、不接受任意 registry，不執行全域清理。基底映像和套件會透過 registry／套件源取得，不包含私人輸入或權重。

沒有 Docker 工具時腳本明確失敗，不寫假成功報告。成功時也只記 `measured_fixture_container_health_only`，不當成真實 GPU 或完整 Compose 驗收。停止可使用相同 compose 檔的 `down`，不加 `-v`，不刪除作品資料。

## 真實 GPU Compose 還需要什麼

Windows `llama-server.exe` 不能當作 Linux 容器引擎。下一最小切片須新增固定內部 engine adapter、經核對的 Linux llama.cpp image digest、只讀本機模型 mount、GPU passthrough、模型 hash／runtime identity 驗證及同步的介面控制，不把 Docker socket 交給 Web API。[llama.cpp 官方 Docker 文件](https://github.com/ggml-org/llama.cpp/blob/master/docs/docker.md)列出其映像與啟動方式；實際 CUDA 相容性及容量仍待驗證。

0.3.0本機MLflow SQLite按需worker已實跑，未容器化；Prometheus目前僅受權限保護的格式出口及產品監控，沒有收集器/server。完整Compose中的這些服務尚未實作。不能把Fixture Compose當完整交付，或把Dockerfile存在當部署完成。
