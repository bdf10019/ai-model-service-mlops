## 1. 計畫書理解

已完整閱讀根目錄的計畫書十三節，包括另外兩個作品及合輯的責任邊界；本次只規劃第一個作品。

產品是讓工程與營運團隊使用的「可客製模型服務控制台」。成功標準是使用者在介面完成選擇設定、推論、評測、比較、發布、監控、恢復與匯出，且每一步能追到後端狀態與證據。產品化、客製化與完整互動優先於追加工具數量。

八月模型是可查驗的外部匯入來源，不是十月重新訓練成果。十月增加的是服務生命週期、身分權限、版本化設定與可操作控制台。模型訓練來源、MLflow 實驗／模型版本、產品發布狀態分別管理。

首版採一個設備事件分流情境；兩組 Profile 共用同一核心。Profile 是設定版本及檢視篩選，不宣稱多租戶隔離。本機工程展示也不等同正式生產、高可用或資安認證。

本輪只新增這三份分析文件；不修改計畫書及八月作品，不安裝、下载、部署、初始化 Git 或啟動模型服務。

## 3. 推薦產品範圍與不做事項

推薦首版支援「繁體中文設備異常事件分流」：使用者提供事件文字及受限欄位，得到事件類型、嚴重度、原文證據、缺失資訊、安全動作代碼與人工複核要求。維修與設備團隊共用這個情境，不加入 OCR、工單寫入或設備控制。

納入：十一個頁面入口、兩個 Profile、真實本機登入與三角色、模型匯入、Fixture／真實推論分流、固定評測、門檻與版本比較、人工核准、單實例發布／回滾、有限排隊、負載測試、監控、追蹤、稽核與非敏感匯出。OpenAI-compatible 僅實作必要且有測試的 models／chat-completions 參數子集，未知參數明確拒絕。

不納入：再訓練／微調／量化平台、RAG 聊天產品、第二及第三作品、合輯、任意外部 Provider URL、雲端帳號及付費模型、任意工具執行、正式多租戶、企業 SSO／TLS 公網部署、全量 OpenAI 協議、多雲、零停機承諾、未實跑 Kubernetes。

## 4. 使用者、角色與旅程

| 角色 | 主要工作 | 可以 | 不可以 |
|---|---|---|---|
| 一般使用者 operator | 處理事件、比較候選、準備變更 | 讀已核准設定／模型；推論；執行配額內評測；編輯設定草稿；提交核准；取消自己的可取消任務；匯出已授權結果 | 套用全域政策、核准自己的發布、部署／回滾、任意提高資源上限、查看秘密 |
| 複核者 reviewer | 判斷結果是否可用、核准品質與設定 | operator 能力；複核結果、比較證據、退回／核准設定及发布候選；探索稽核 | 核准自己的提案、變更帳號權限、繞過硬門檻、直接執行部署 |
| 管理者 admin | 維運、資源、服務恢復 | 管理帳號／預設 Provider 參照、設定平台上限；执行已核准發布；進入維護模式；受控重啟與回滾 | 任意修改歷史證據、降低安全底線、以管理者身分繞過發布核准 |

採本機帳號、後端 session 與 CSRF／Origin 檢查；不是前端切換角色即取得權限。示範帳號首次引導設定密碼，不能內建固定密碼。首位管理者建立採一次性本機 bootstrap，成功後關閉入口。Profile 的核准角色只可選受支援模板及已授權 reviewer，不允許把一般人升格。

旅程：首次健康檢查與登入 → 選 Profile → 匯入／選候選模型 → Playground → 固定評測 → 比較與送審 → reviewer 核准 → admin 發布 → 監控／告警 → 回滾或恢復 → 匯出證據。未發布前可對候選做沙盒推論；業務推論只使用已發布版本。

## 5. 兩組原創設定及行為差異

設定是設計範例，尚無可被程式載入的正式 Schema。兩組皆使用同一 Q8 候選，Fixture 另列測試模式。品質數字在基準後填入，未填或未評測不可發布；下列資源數字只是假定的保守試跑參數，不是效能承諾。

| 設定層 | 維修服務團隊：維修分流台 | 設備管理團隊：設備守望台 |
|---|---|---|
| 品牌／術語 | 原創文字標誌；藍綠；「案件、接案、待複核」 | 原創文字標誌；靛灰；「設備事件、風險審查、待發布」 |
| 首頁重點 | 我的待處理案件、缺失資訊與佇列 | 風險分布、發布狀態、回歸與告警 |
| 支援任務 | 同一事件分流；摘要與接案資訊 | 同一事件分流；風險摘要与資產資訊 |
| 必填輸入 | incident_text、asset_id；contact_window 可選且限定非個資枚舉 | incident_text、asset_id、asset_criticality 枚舉；maintenance_window 狀態 |
| 輸出形狀 | 共用安全核心＋接案欄位別名 | 共用安全核心＋資產重要性與審查理由；不得擴成另一種模型任務 |
| Prompt | triage-service-v1；允許調整語氣、摘要重點及白名單變數 | triage-asset-v1；强调未知資訊及資產重要性，仍保留同一安全核心 |
| 結果複核 | high／critical、unknown、注入、無效／缺證據必審；其餘可完成 | 維修版條件再加 medium，以及關鍵設備的所有事件必審 |
| 品質閘門 | raw schema、event F1、severity F1、拒答指標；數值待基準 | 同指標；severity 與關鍵設備切片不得低於維修版要求；數值待基準 |
| 發布核准 | 一名非提案者 reviewer 核准，admin 執行 | 兩名不同 reviewer 核准且均非提案者，admin 在本機設定的維護時段執行 |
| 路由／發布 | 單一已發布 release 指標；手動完整切換 | 同一策略，但增加維護時段及第二核准；首版無 Canary |
| 試跑資源草案 | engine concurrency 1、queue 4、queue timeout 10s、generation timeout 60s | engine concurrency 1、queue 2、queue timeout 5s、generation timeout 60s |
| 告警與匯出 | 案件失敗／等待摘要，JSON＋CSV＋Markdown 報告 | 風險、版本差異及完整核准鏈摘要，同樣三種格式 |

同一輸入示例：`asset_id=DEMO-PUMP-07；事件=泵浦持續震動，但未提供量測值`。不含公司、個資或真實資產。

1. 設備版缺 asset_criticality 時在前後端均拒絕；維修版接受進入推論。這是欄位層差異。
2. 補齊相同測試輸入後，若得到相同且證據有效的 medium 結果，維修版可完成，設備版進待複核。這一政策案例用明示 Fixture 保證分支可重現，再另跑真實模型記錄實際結果，不能偽造真實模型必定輸出 medium。
3. 對相同合格發布包，維修版一人核准後可由 admin 發布；設備版仍等待第二 reviewer 及維護時段。這是後端狀態機差異。
4. 切換 Profile 或修改草稿不重算舊任務；任務保留啟動時完整設定快照與版本。Profile 套用不會暗中切换线上 release，線上使用的設定屬於已核准發布包。

### 設定中心的邊界

表單 → 結構／範圍驗證 → 保存草稿 → 用合成案例預覽 → 與基準版比較 → 提交／核准 → 確認影響後套用 → 產生不可變版本。支援 JSON 匯入／匯出、還原預設及上一版；還原同樣產生新版本並保留審查，不刪除歷史。

未知欄位與未知 schema_version 拒絕；禁止遠端 `$ref`、可執行模板、任意 Jinja、SQL、命令、動態套件與任意 URL。Schema 只允許已支援欄位型別、枚舉、長度及有限深度。Logo 限合法點陣圖並重編碼，首版提供原創文字標誌；不接受主動內容 SVG／外連 URL。報告格式與儀表板元件均為白名單。

安全底線由程式獨立控制，Profile 只能更嚴格。Secrets 僅保留 secret_ref／遮罩；匯入含疑似秘密值直接拒絕，錯誤訊息不回顯值。允許的 Provider endpoint 由後端固定登記，不讓表單導向任意網路位置。

### 模型與資料建議

Base revision 為 `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e`。官方模型庫目前標示 Apache-2.0；固定 revision LICENSE 網頁本輪取得失敗，正式匯入前仍須取得與保存該版本授權文字、衍生說明與本地來源契約，不能只靠模型名稱。[官方模型來源](https://huggingface.co/Qwen/Qwen3-1.7B/tree/main)

資料採原創合成設備事件：舊 210 test＋14 challenge 只作已知回歸參考；另建立與模板／情境家族隔離的十月保留測試集及 Profile 行為案例，封存後不反覆調參。規劃每個事件類型、風險等級、缺欄、注入、拒答與格式失敗均有案例；最終樣本數於資料設計時定稿。歷史 test/challenge 曾用於迭代，不能稱為全新未觸碰測試集。原創資料授權候選 CC BY 4.0；不使用真實公司事件。

Fixture 是確定性測試 Provider，其 schema、延遲注入、錯誤、過载與逾時可以測工程流程，但其品質／速度不算模型成績。Fixture release 只存在測試沙盒，正式發布路徑始終拒絕。

| 持久化 | 產品 SQLite（單控制程序）、版本化 artifacts／reports；有限背景工作 | 首版僅單實例，短交易與有界 job lease；不聲稱跨副本共享佇列 |
| MLflow | 獨立 SQLite backend＋專案內 artifact root；Run／Model Registry 由產品後端操作 | Registry 需要 DB-backed store。以明確 GGUF flavor／模型包封裝契約登記，避免僅記 artifact 卻宣稱完成模型登記。[官方 Backend Store](https://mlflow.org/docs/latest/self-hosting/architecture/backend-store/) |
| Registry 關係 | MLflow 記實驗與模型版本；產品 DB 記核准、release bundle、實際載入與發布狀態 | alias/tag 可以輔助索引，不能把 alias 變更當成部署。MLflow 同步失敗要重試／阻擋核准，不得假成功。[官方 Registry 工作流](https://www.mlflow.org/docs/latest/ml/model-registry/workflow/) |
| 監控 | prometheus-client＋Prometheus；控制台自有圖表 | 不再堆疊 Grafana、Loki、Tempo；指標設 bounded labels，不以 request_id 當 label |
| 測試 | pytest、前端互動測試、Playwright；固定設定 Python/httpx 負載驅動器 | 負載引擎由介面觸發，固定輸入／設定並匯出機器報告；不是僅 CLI |
| 容器 | Compose：控制台/API、引擎、MLflow、Prometheus | 使用固定服務清單，預設只綁 127.0.0.1；WSL／Docker 安裝與儲存位置須另行核准 |

發布控制器只允許啟動、停止、健康檢查作品自己的引擎及既定 release。Web API 不掛整個 Docker socket，不接受任意 compose 路徑、映像、volume 或 shell。完整 Compose 首次啟動可用安裝腳本；產品啟動後模型部署、重試與回滾必須在工作台操作並連到真實程序行為。

部署採停止接新工作 → 有界排空 → 保存 previous-good → 載入候選 → 健康與真實 canary 請求（此處指固定冒煙請求，非流量 Canary 發布）→ 原子更新 active 指標。失敗恢復上一版；單 GPU 首版承認維護期間中断，不承諾雙模型同駐與零停機。

### 串流與安全

llama.cpp 官方文件提供串流及 schema-constrained JSON 能力，但本地鎖定 build 的事件格式與取消語意仍待實測。[官方 server 文件](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)

建議日常結果先完成 Schema／證據／安全驗證再呈現；進度事件只反映排隊、生成、驗證階段。另設 reviewer/admin 的「合成案例串流診斷」，由後端限制只能選固定合成案例，顯示真實生成增量且標示未驗證、不供業務使用，完成後另呈現正式結果。若只收到 SSE 文本 chunk 而不能證明第一 token 時刻，名稱用「首文字片段延遲」，不能冒稱 Token-level TTFT；引擎時間與客戶端可見時間分開。

## 8. 品質、效能、安全與產品驗收

### 品質與發布

- 每次評測封存 model/artifact hash、engine build、Prompt／Schema／policy／Profile 版本、資料 manifest、scoring 版本、生成設定與環境。不同契約報告只能描述性並列，不能算公平回歸。
- 分別呈現原始模型品質與政策後結果：event／severity macro-F1、原始 JSON Schema 合格率、必要欄位、原文證據精度、高風險轉複核、拒答／誤拒答、unknown、人工介入率及每類失敗數。
- 系統安全底線：高風險／無效／無證據輸出必須 fail closed；故意注入不能改權限或觸發設備動作。封存安全測試中出現任何違反即拒絕發布；這是有限測試集上的工程條件，不是世界範圍安全保證。
- event F1、severity F1、raw schema 及可接受回歸數字由開發集和初始基準訂定並版本化，再封存驗收集；未定稿一律標「待訂」，不能先發布再補數字。UI 展示 observed、operator、threshold、pass/fail、reason、case links。
- 核准綁定完整 release bundle hash，包含模型、Prompt、Profile、政策、引擎與評測報告。任一項變更使核准失效。自我核准、過期報告、錯誤 hash、Fixture 與舊成功報告偷換新模型均須被後端拒絕。
- 發布核准同時綁定允許的 previous-good 恢復目標及恢復政策；admin 可執行這個預先核准的恢復方案並記錄原因。目標被撤銷、hash 改變或不符合現行安全底線時拒絕，不能用「緊急回滾」繞過品質與權限。
- 模型版本回滾只有在兩個不同模型 artifact 均重新通過新閘門時才宣稱完成；只有一個合格 artifact 時，先驗證同模型不同 Prompt／設定的「服務版本回滾」，明示其邊界，不用複製檔案假造第二模型。

### 效能

- 固定輸入集合、輸入／輸出上限、temperature、seed（支援時）、每 slot context、預熱、持續時間／樣本數、併發與排隊條件；冷啟動與熱穩態分開。
- 量測 HTTP 端到端 P50／P95、queue wait、engine generation、首次 token／片段（能力不足則 N/A）、最終驗證完成時間、請求吞吐、實際 token throughput、錯誤／逾時／拒絕率及 RAM／VRAM。
- 延遲分母及排除規則明示；失敗不從成功率消失，成功延遲不冒充全請求延遲。每張圖可鑽取原始樣本與來源版本。
- 先 concurrency=1 探查，再逐級試 2、4（若健康與資源預算允許），超載即中止升級。數字只是測試層級，並非承諾支援四併發。
- 負載目標僅可選本作品登記的本機 deployment_id，不能輸入任意 URL；總工作量、執行時間及輸出有硬上限，避免工作台成為流量攻擊工具。
- HTTP 逾時／斷線不等於 GPU 工作已停止；未確認終止前保留容量槽。排隊可取消，生成若只能要求取消則顯示「取消中」，不能立刻假報完成。
- 回滾計時由後端接受已授權操作至上一版實際健康且推論成功；另記偵測耗時、排空、卸載、載入與驗證。故障恢復測同程序失效、服務重啟及未完成任務狀態復原。

### 安全、資料與恢復

- 每個 mutation 同時測允許及越權，含直接 API 越權、CSRF、自我核准、舊版本核准、重複點擊、並發發布；用 idempotency key＋版本條件避免重複副作用。
- 匯入防 traversal、symlink／reparse point、未知 archive 內容、超大檔、hash mismatch；僅接收安全檔案類型及固定來源。模型 bytes 與 manifest 分開，SHA-256 是內容完整性，不是作者身分簽章。
- 使用者輸入只送本機引擎；日志不存原文、密碼、Token 或私人路徑。結果保存與重播只對合成示範集預設開啟；一般文字預設短暫處理，若需要保存原文另決定留存政策。
- 匯出用內容允許清單，包含版本、遮罩事件、報告及 hash，不含秘密、內部絕對路徑、帳號識別或權重；CSV 防公式注入。跨 Profile 可見性清楚標示為同一安裝範圍，無隔離主張。
- SQLite 短交易、任務租約、啟動 reconcile、寫入暫存後原子移交；中斷推論標失敗可重試，不自動重放發布。MLflow 操作用 outbox 重試与唯一識別，防止一份結果多次登記。
- 提供單實例備份／還原流程；備份要一致性快照与校驗，介面還原需管理者、維護狀態及影響確認。歷史報告不原地改寫，本機 append-only／hash 校驗不宣稱外部不可變稽核。
- 狀態備份與公開證據匯出分開：備份可能包含帳號與私有狀態，只留在作品內受控且 Git 忽略的位置，不可混入可分享報告包；還原不接受未驗證的任意資料庫檔。

### 產品驗收

- 後端單元／整合、前端元件／表單、Playwright 全旅程；響應式桌機／平板／手機、鍵盤焦點、標籤、非純顏色狀態。
- 成功、載入、空、验证錯誤、失敗、逾時、無權限、可恢復提示逐頁驗證。重整、切換 Profile、服務重啟後資料與版本一致。
- 全矩陣逐列驗證 UI 操作→後端狀態→證據；分別計算「規劃覆蓋、實作覆蓋、驗收通過」，不得用規劃矩陣冒稱完成 100%。
- 標示 measured／fixture／estimated／not-run；本輪無建置／部署／推論測試，只有文件及唯讀探查。

## 10. 主要風險與待決定事項

1. **首版正式目標與系統變更時機**：建議保留 Compose 為正式最小交付，先完成單模型垂直切片與基準，隨後另提 WSL／Docker 變更單。安裝可能啟用 Windows 功能、重開機、占用 RAM／磁碟及建立系統儲存；屆時列安裝內容、儲存路徑、限制与恢復方式再取得同意。本次方向確認不是安裝授權。
2. **模型再利用**：建議從現有 Q8 複製匯入並重新評測，保留歷史訓練證據缺口；NF4 第二模型延後。不以旧发布状态给新服务免验资格。若要求第一版就证明不同权重间回滚，需增加第二个合格真实模型与评测工作。
3. **任務邊界**：建議只有繁體中文設備事件文字分流，不加入 PDF／OCR、維修步驟生成或工單寫入。Profile 按本文件三層差異設計。
4. **串流與留存**：建議業務結果驗證後呈現；逐 Token／chunk 診斷限固定合成案例及 reviewer/admin。一般輸入預設不保存原文；是否要首版提供明確同意後的保存／重播，是產品與隱私範圍決定。
5. **交付與時間取捨**：建議完整本機產品及 Compose 優先，Kubernetes 延後。若有硬性展示日期，需据此縮減已選功能或延後進階項，不能刪除已交付功能的互動／安全／測試入口。
